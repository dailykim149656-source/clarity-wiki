# 요구사항에서 검증 보고까지

현재 요청에 필요한 단계부터 시작한다. 이미 충분한 계약과 근거가 있으면 다시 질문하거나 승인을 받는 절차를 만들지 않는다.

## clarify: 자료부터 확인

README, 요구 결과, 입력 스키마, 기존 구현, 제약을 읽고 원문 위치를 기록한다. 문서가 답하는 내용을 다시 묻지 않는다. 완료 기준이나 구현 선택을 바꾸는 질문만 **최대 3개**로 추린다. 정보가 충분하면 질문 없이 진행한다.

미답변은 `가정 / 근거 / 바뀌면 영향 / 확인 주체`로 남긴다. 가정을 공식 정책으로 쓰지 않는다. 결정이 필수인 부분만 보류하고 독립적인 작업은 계속한다. 외부 담당자에게 묻는 질문은 초안으로 제시하며, 발송은 사용자가 허용한 경로와 범위를 따른다.

## contract: 관찰 가능한 완료 기준

| ID | 요구사항과 원문 위치 | 완료 기준 | 검증 방법·입력 | 상태 |
|---|---|---|---|---|
| R1 | 해당 문서의 파일·절·행 | 성공/실패를 판별할 값이나 동작 | 시나리오·명령·예상 결과 | 미검증 |

`잘 작동함` 대신 정상 사례와 중요한 예외에서 관찰할 결과를 적는다. 새 작업의 결과를 주장할 때는 확인된 근거 범위로 한정한다. 기존 글을 윤문할 때는 원래 주장을 유지하고 사실 검토 의견을 분리한다.

한 개의 [작업 기록](../examples/work-record.md)에 요구사항·결정·검증을 모으면 충분하다. 세부 명세가 필요한 다음 단계에서만 [계약 참고](plan/contract.md)를 선택한다. 문서 이름은 프로젝트 요구에 맞춘다.

## verify: 실행과 근거 연결

요구사항 ID마다 실제 입력, 실행 명령 또는 수동 절차, 관찰 결과, 근거 파일을 연결한다. 검증이 코드나 입력 수정 전에 실행됐다면 재실행하고 근거를 갱신한다. 실행 실패·미실행·환경 차단을 구분한다. AI가 수행한 확인과 사람이 직접 한 확인도 구분한다.

자동 점검이 필요할 때 조건부 [로컬 검사](local-checks.md)를 읽는다. `audit`는 수치·단위·인용 등의 변경 후보를, `evidence`는 산출물과 증거 연결·해시를 검사한다. 두 도구 모두 실제 업무 검증을 대신하지 않는다. 명령 문자열은 기록이며 검사 도구가 실행하지 않는다.

## report: 결과와 한계

실제 결과를 먼저 쓰고 채택·기각한 판단과 근거, 수행한 검증, 미검증 범위·영향을 잇는다. 실패나 누락을 완료로 표현하지 않는다. 원본과 보고서의 수치·대상·인용·조건을 대조한다. 윤문이 필요하면 다음 단계의 주 문서를 [technical](rewrite/technical.md)로 교체한다.

외부 발송·게시·제출은 기존 사용자 승인 범위 안에서 처리한다. 이 Skill의 사용만으로 외부 조치 권한이 생기지 않는다. 환경별 제한은 해당 환경 프로필이 적용될 때 확인한다.
