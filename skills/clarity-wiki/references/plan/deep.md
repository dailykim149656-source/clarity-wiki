# 기획: Socratic Deep (심층 인터뷰)

**언제**: 비용이 큰 제품 결정, 신규 서비스 구상, 이해관계자가 다수인 기능, 재작업 위험이 높은 설계. 시간 제한이 매우 짧으면 사용하지 않는다.

## 단계

1. **Existing evidence**: 문서, 현재 코드, 조직 규칙, 기존 실험을 먼저 확인한다.
2. **Problem ontology**: 해결하려는 문제를 어떤 단위로 정의하는가? 용어/경계/주체를 명확히 한다.
3. **Assumptions ledger**: 확인됨, 확인 대기, 논쟁 중, 결정권자 필요 네 상태로 모호성을 기록한다.
4. **Socratic interview**: 가장 큰 설계 차이를 만드는 질문 최대 3개를 추려 묻고 이유를 짧게 설명한다. 미답변은 가정과 영향으로 기록한다. 연속 질문으로 실행을 미루지 않는다.
5. **Options**: 2~3개의 실행 가능한 대안, 비용, 리스크, 포기해야 하는 것들을 비교한다.
6. **Restatement**: 사용자 목표와 비목표를 재진술하고 잘못 이해한 부분을 확인한다.
7. **Closure**: 결정적 불확실성이 해소되거나 명시적으로 보류될 때 실행 계약을 만든다.

## 질문 축 예시 (상황에 맞는 것만)

- 개념: '품질 이상'은 측정치 초과, 특정 불량 패턴, 고객 영향 중 무엇인가?
- 관찰: 지금 확인한 증거가 없다면 무엇을 참이라고 가정하는가?
- 반례: 어떤 사례 하나가 지금 설계를 틀리게 만드는가?
- 행동: 분석 결과를 보고 누가 무엇을 할 수 있는가? 자동 변경은 가능한가?
- 검증: 구현 후 어떤 행동/로그/데이터로 성공을 확인할 수 있는가?

## 종료 조건

- 성공 기준과 필수 결과물이 명확하다.
- 실행 차이를 만드는 미확정 사항에 책임자나 보수적 기본값이 연결된다.
- 현실적인 검증 방법이 있다.
- 외부에 영향을 주는 변경에 승인 주체가 있다.

조건부 보조 문서는 [실행 계약](contract.md) 또는 [반례 검토](stress.md) 중 하나만 선택한다. 사용자가 이미 상세 지시를 줬다면 장시간 인터뷰를 강요하지 않는다.
