# 윤문: Technical (보고서와 기술 문서)

**언제**: README, 검증 보고서, 채용 문서, 업무 메일, 발표 자료, 연구 및 기술 설명.

## 작성 순서

1. 맨 앞에 독자가 알아야 할 **결론 또는 실제 결과**를 배치한다.
2. 다음에는 입력/방법/검증/한계 순서로만 필요한 문단을 채운다. 항목 제목은 과제 요구에 맞춰 바꾼다.
3. 대상을 뜻하는 명사는 정확히 유지한다. 모델명, 변수, 파일 경로, 버전, 단위, 임계값, 날짜, 인용을 변경하지 않는다.
4. `분석을 수행하였다`보다는 실제 동작을 명확히 쓰되 전문 용어는 살린다.
5. AI가 수행한 조치와 사람이 직접 확인한 조치를 구분한다.
6. 윤문에서는 미확인 수치나 인과 주장도 원문의 강도 그대로 보존한다. 근거 부족은 수정 본문 밖의 `검토 의견`에 표시한다. 사실 교정까지 요청받았을 때만 근거를 확인해 수정한다.
7. 완료 기준, 테스트 결과, 미완성 범위를 구조화해 다음 담당자가 재현할 수 있게 한다.

## 검증된 보고서에서 권장하는 최소 구성

- 목적: 무엇을 결정하거나 해결하려는가?
- 결과: 무엇이 실제로 작동하거나 확인됐는가?
- 증거: 어떤 파일, 행, 로그, 테스트로 확인했는가?
- 한계: 추가 확인이 필요한 부분은 무엇인가?
- 제안: 즉시 실행할지, 사람 승인을 받을지, 보류할지?

## 금지

- 원문에 없던 성과 수치, 사례, 회사 내부 정보, 원인 단정을 만들어내지 않는다.
- '검증했다'는 말을 실제 확인 기록 없이 붙이지 않는다.
- 미완성을 완료로 표현하거나, 장황한 추상적 의미 부여로 실패를 가리지 않는다.
- 서술형 평가에서는 AI 사용 금지 시 해당 지시를 따라야 한다. 그 단계에 AI를 사용하거나 결과를 만들어 제공하도록 조언하지 않는다.

**조건부**: 사실 대조가 필요하면 [의미 보존 검사](fidelity.md)를 보조 문서 하나로 선택한다. 새 보고서의 검증 근거를 정리하는 단계라면 [작업 흐름](../workflow.md)으로 주 문서를 교체한다.
